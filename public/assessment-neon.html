Assessment: Neon MCP server

Leslie Kadenge · a public server I didn't write, read against the two-tier method

Neon runs serverless Postgres, and their MCP server does something most don't: it enforces read-only through the OAuth scope the token was granted, so a read-only connection literally cannot be handed a writing tool. That's a stronger guarantee than a config flag the server checks itself. Generous, verifiable read.

The standout

The standout is the access model. Read-only isn't a boolean the server inspects — it's carried in the OAuth scope granted at authorization, with an approval dialog at connect and the tool list filtered to what the scope permits. A connection granted read-only scope is never even offered the mutating tools. That's defense in depth done at the right layer: the guarantee lives in the grant, not in a check the server has to remember to run. Tools are annotated, and the server is well tested (~50 test files).

Verdict

Access done right. Putting read-only in the OAuth scope rather than a server-side flag is the strongest form of that guarantee, and the approval dialog makes the grant explicit. The open tier-two item is per-action confirmation: once a write scope is granted, an individual destructive call isn't separately confirmed. Sound on the basics, ahead on the access model.
