How I review an MCP server

Leslie Kadenge · the standard, applied the same way every time

This is the checklist behind every assessment I publish and every review I'm paid for. It's here in the open for one reason: a review is only worth anything if you can see what it looked for. A grade with no method behind it is a number; a method you can read is a standard.

An MCP server is a program that hands an AI model the keys to something real — a database, a filesystem, a cloud account, a web session. The questions below are the ones that decide whether those keys can be misused, and every one is answered by reading the code and running it, not by pattern-matching the source. Where a check can be settled by executing the thing rather than trusting a comment, I execute it.

The one rule everything rests on

A safety property you can only read in a README is not a safety property. The ones that count are the ones a machine enforces or a test proves.

Every check below is really the same question asked eight ways: is this guarantee something the code makes true, or something the docs merely claim?

1 — Tool annotations

Does every tool declare readOnlyHint, destructiveHint and openWorldHint, and are they correct? These are the only machine-readable way a client can know which tools are safe to run unattended and which need gating. A destructive tool with no destructiveHint is a delete a host cannot see coming. I check coverage across every tool, not a sample — and whether the annotations match what the tool actually does.

2 — Destructive-operation gating

For anything that deletes, writes, sends or spends: is there a confirmation step at all? Is the dangerous path a dry run by default? And — the one most servers miss — can the same approval be spent twice? The SDK binds and expires approval state but does not consume it; closing that gap is the server's job, not the SDK's.

3 — Path handling

The classic file-write bug: a tool takes a caller-supplied path, resolves it, and acts — without checking the result stayed inside an allowed directory. I look for four things: a root allowlist that denies by default; a symlink check that runs before the path is resolved, not after (resolving first inspects where the link points, not the link); a re-check at the moment of the destructive action, not trust in a stale scan; and identifiers rather than raw paths where possible.

4 — Query and injection safety

For database and query tools: is "read-only" enforced by parsing the SQL or by pattern-matching it? Are multiple statements accepted (SELECT 1; DROP …)? Can a write hide in a CTE? Does the database login also lack write permission, as a second layer? Pattern-matching a query is not the same as understanding it, and the gap between the two is where the bypass lives.

5 — Untrusted content

Servers that read the open web, a database, or the filesystem pull in content their user did not write. Does that content flow back into the model's context marked as untrusted, or does a web page's text arrive in the same channel as the user's instructions? On a tool whose whole purpose is reading things you don't control, openWorldHint is the difference between the host treating a result as data and treating it as a command.

6 — The access model

Least privilege, checked at the design level. Does the agent choose the scope — the roots, the database, the account — or is that fixed when the server starts? Does an empty or missing configuration deny everything, or default to the whole world? A misconfigured server should be useless, not dangerous.

7 — Tests and CI

Every safety property above is a claim. A claim without a test is a hope. I look for a test behind each dangerous path — and, just as important, whether CI actually runs them on every commit. A careful guard with no CI is one careless merge away from being gone, and nobody would know.

8 — Claim versus reality

Finally, the whole thing read against its own README. Where the docs promise "read-only" or "safe by default", is that enforced, or asserted? Is there a full write path sitting unused in the codebase, one wired-up call from making the promise false? This is the check that ties the other seven together: the distance between what the server says about itself and what its code makes true.

What you get

A paid review runs every one of these against the whole server and writes up what it finds — each finding with a test that proves it, and each safe area noted as checked rather than skipped. The result is a document you can forward to whoever asked whether anyone had looked: an enterprise customer's security team, a compliance reviewer, a partner's vendor questionnaire.
